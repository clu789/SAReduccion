# Matriz de Requerimientos de SAReducción

## 1. Información general del proyecto

**Nombre del proyecto:** SAReducción  
**Propósito:** Gestionar solicitudes de reducción del monto de inscripción y reinscripción para hijos o cónyuges de trabajadores del Tecnológico Nacional de México y personal homologado.  
**Perfiles principales:** Estudiante, Aspirante y Administrador.  
**Arquitectura documentada:** Frontend web, backend Spring Boot, base de datos Oracle y despliegue mediante Docker Compose.  
**Estado de la rama:** Documento elaborado a partir del contenido disponible en la rama `dev`, sin considerar una funcionalidad como implementada únicamente por estar descrita en la arquitectura.

## 2. Objetivo del documento

Establecer de forma formal, verificable y trazable los requerimientos funcionales y no funcionales que deben cumplirse en SAReducción.

## 3. Alcance de los requerimientos

El alcance comprende autenticación y autorización, gestión de perfiles, paneles de solicitantes, convocatorias, solicitudes, formularios dinámicos, respuestas, revisiones administrativas, deducciones, historiales, montos oficiales y notificaciones por correo electrónico.

Este documento no convierte una capacidad propuesta o un procedimiento existente en una integración implementada; las reglas y capacidades se describen como requisitos del sistema.

## 4. Actores del sistema

| Actor | Descripción |
| --- | --- |
| Estudiante | Usuario identificado mediante una cuenta Oracle asociada a su número de control. Consulta convocatorias y solicitudes, registra solicitudes y puede retirarlas o corregirlas según su estado y plazo. |
| Aspirante | Usuario identificado mediante ficha y CURP dentro de su periodo y año académico. Consulta convocatorias y solicitudes, registra solicitudes y puede retirarlas o corregirlas según su estado y plazo. |
| Administrador | Usuario autorizado que revisa solicitudes, administra deducciones, configura convocatorias y montos, consulta historiales y envía notificaciones. |
| Sistema de correo | Servicio SMTP utilizado para enviar avisos del trámite y diagnósticos de entrega. |


## Estado de revisión

**Leyenda:**

| Estado | Significado |
| --- | --- |
| Implementado | Existe integración identificada en la rama `dev`, con código o estructura respaldada por el backend, frontend o Oracle. |
| Parcial | Existe una implementación base, pero falta completar integración, cobertura o validación. |
| Pendiente | No se encontró evidencia suficiente de implementación o integración en la revisión. |
| Acordado | Es una decisión o restricción explícita del proyecto que no requiere una implementación adicional medible. |

El estado describe la evidencia encontrada en el repositorio en esta revisión y no sustituye una aprobación formal de pruebas.

## 8. Observaciones y decisiones pendientes

1. El documento conserva los estados adicionales respaldados por la base de datos `RETIRADO` y sus transiciones. `RETIRADO` no sustituye al término de cancelación utilizado en los requisitos generales.
2. La actualización de datos personales del estudiante o aspirante no está respaldada por un flujo confirmado en los documentos; este documento incluye solamente la consulta del perfil. Cualquier edición deberá resolverse antes de implementar.
3. La integración institucional de recibos de pago y comprobantes no está confirmada y queda fuera del alcance obligatorio actual.
4. Oracle XE 21c es la plataforma actual documentada. Oracle 12c requiere validación independiente y no se considera compatible hasta probar scripts, objetos, permisos y `SAR_LOAD_DEV_SEED=false`.
5. La fuente institucional de correo para estudiantes no está confirmada; el paquete administrativo actual solo obtiene correo de aspirantes.
6. La verificación de aspirantes por correo y código temporal puede considerarse una ampliación mientras se mantiene la autenticación provisional con ficha y CURP.
7. No se han acordado métricas numéricas de rendimiento, disponibilidad, recuperación ni tiempo máximo de respuesta.
8. No se ha establecido un estándar cuantitativo de accesibilidad adicional a los criterios de usabilidad y adaptabilidad documentados.
